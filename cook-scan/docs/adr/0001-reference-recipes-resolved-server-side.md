# 参照レシピはサーバー側で recipe_id から解決する

AIレシピチャットに既存レシピを「参照レシピ」として持ち込む際、クライアントは選択した `referenceRecipeIds`（IDの配列）だけを送り、サーバーが `userId` で所有権を検証したうえでDBから取得し、文脈に整形して注入する。クライアント側でレシピ内容をテキスト整形して送る案（既存のレシピ下書きの context と同じ方式）も検討したが、本人のレシピだけを参照できるという所有権保証と、常に最新・正確なデータを使える点を優先してサーバー解決を選んだ。

## Considered Options

- **クライアントで整形して content に埋め込む**（既存の下書き context と同方式）: サーバー改修ゼロで済むが、クライアントが任意のレシピ内容を捏造して送り込める余地が残り、表示用に丸めた値や古いキャッシュが混入しうる。却下。
- **サーバーで recipe_id から取得**（採用）: API契約に `referenceRecipeIds` を追加し、`userId` でフィルタして取得。所有権検証とデータ正確性が保証される。

## Consequences

- チャットAPI（`/api/recipes/generate`）が新たにDBアクセスを持つ。既存のレシピ下書き context はクライアント整形のままなので、「なぜ参照レシピだけサーバー解決なのか」は本ADRが理由を示す。
- 参照IDが一つでもDBに見つからなければエラーを返す（部分成功させない）。削除済みレシピの参照は選び直しを促す。
- 参照レシピはセッション中保持され、クライアントが送信のたびに `referenceRecipeIds` を送り続ける（サーバーはステートレスを維持）。
